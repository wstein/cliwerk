= cliwerk and upstream picocli
:toc: preamble

cliwerk is an independent, long-lived fork of https://github.com/remkop/picocli[picocli] by Remko Popma,
maintained by https://github.com/wstein[wstein] at https://github.com/wstein/cliwerk.
This page describes how the fork relates to upstream, how its branches are used, and the rules for its name.

== Relationship to upstream

* cliwerk started as a fork of picocli and keeps picocli's code, history and license
  (Apache License 2.0, see `LICENSE` and `NOTICE`).
* cliwerk is *not affiliated with or endorsed by the picocli project*.
  Problems found in cliwerk should not be reported to the picocli project unless they are
  reproducible with an upstream picocli release.
* The library API is still picocli's: the Java package is `picocli` and the upstream user manual at
  https://picocli.info applies to everything cliwerk has not changed.
  cliwerk is meant as a drop-in replacement for upstream picocli, see <<Compatibility with upstream picocli>>.
* cliwerk adds features on top of picocli (fish shell completion, `picocli-spec`, `picocli-spec-tool`,
  on-demand help sections; see the `README.md` and `CHANGELOG.md`).
  Some of them are proposed upstream as well (fish completion: https://github.com/remkop/picocli/pull/2463[remkop/picocli#2463]);
  whether upstream accepts them does not affect their availability in cliwerk.

== Compatibility with upstream picocli

cliwerk is a *drop-in replacement* for upstream picocli (decided 2026-10-24, see <<Decision log>>):

* The Java package stays `picocli`, and all public API names (classes, annotations, methods, attributes)
  stay as they are in upstream picocli. Only the Maven coordinates differ from upstream.
* Rule: the public API of `picocli.*` stays *additive*. cliwerk may add public types and members,
  but does not remove or incompatibly change public API that upstream picocli provides.
  Removing or changing public API needs a deliberate exception, recorded in the <<Decision log>>
  with the affected API and the reason.
* Consequence: cliwerk and upstream picocli (`info.picocli:picocli`) cannot be on the same classpath.
  Both contain the same fully qualified class names (`picocli.CommandLine`, ...), so whichever jar comes first wins.
  Because the Maven coordinates differ, Maven and Gradle do not see this as a version conflict and will not resolve it for you.
  If a dependency brings in upstream picocli transitively, exclude it or substitute cliwerk for it.
  Since the API is additive, code compiled against upstream picocli keeps working with cliwerk.
+
Maven, on each dependency that brings in upstream picocli:
+
[source,xml]
----
<dependency>
  <groupId>com.example</groupId>
  <artifactId>some-library</artifactId>
  <version>1.0</version>
  <exclusions>
    <exclusion>
      <groupId>info.picocli</groupId>
      <artifactId>picocli</artifactId>
    </exclusion>
  </exclusions>
</dependency>
----
+
Gradle, for all configurations, either exclude upstream picocli:
+
[source,groovy]
----
configurations.all {
    exclude group: 'info.picocli', module: 'picocli'
}
----
+
or substitute cliwerk for it (`using` needs Gradle 6.6 or later;
use the current coordinates until the new ones of <<Coordinates and distribution>> are implemented):
+
[source,groovy]
----
configurations.all {
    resolutionStrategy.dependencySubstitution {
        substitute module('info.picocli:picocli') using module('io.github.wstein:picocli:<version>')
    }
}
----
* Renaming the Java package (for example to `cliwerk`) remains possible later, but is deliberately deferred:
  it would touch almost every source file and make every upstream merge conflict broadly.

== Coordinates and distribution

Decided 2026-10-24, *not yet implemented*:

* groupId `io.github.wstein`, artifactId `cliwerk` for the core library (published today as `io.github.wstein:picocli`).
* Other modules follow their module names with `picocli` replaced by `cliwerk`, if and when they are published:
  `cliwerk-codegen`, `cliwerk-groovy`, `cliwerk-shell-jline2`, `cliwerk-shell-jline3`, `cliwerk-spring-boot-starter`,
  `cliwerk-spec` and `cliwerk-spec-tool`.
  Today only the core artifact is published (`gradle/publish-fork-repo.gradle` is applied in the root project only);
  when built with Java 11 or later it also contains the `picocli-spec` classes.
* Distribution stays the existing flat Maven repository on GitHub Pages, at its new address after the repository rename.
  Intended address: `https://wstein.github.io/cliwerk/maven` (to be verified by the owner).
  The publishing setup (`gradle/publish-fork-repo.gradle`, `.github/workflows/release.yml`) and the GitHub Pages URLs
  in the documentation have not been changed yet.
* Maven Central only later, if cliwerk is to be used by others.

== Versioning

Decided 2026-10-24, applied with version `4.7.7.1`:

* cliwerk versions have four numeric parts: `<upstream x.y.z>.<fork revision>`.
  The first three parts are the upstream picocli release whose API is the baseline;
  the fourth part is the cliwerk revision on top of it, starting at 1.
* The current base is upstream picocli *4.7.7*, the latest upstream release when this was decided
  (remkop/picocli GitHub releases and Maven Central; released 2025-04-19).
  The first cliwerk version under this scheme is therefore `4.7.7.1`, followed by `4.7.7.2`, ...
  When upstream publishes a new release and it is merged (see <<Upstream syncs>>),
  the base moves to that release and the revision starts at 1 again (for example `4.7.8.1`).
* Why not a qualifier such as `4.7.7-cliwerk.1`: Maven and Gradle order unknown qualifiers differently.
  Maven sorts `4.7.7-cliwerk.1` after `4.7.7`, Gradle sorts it before `4.7.7`.
  A purely numeric fourth part is ordered the same way by both (`4.7.7.10` after `4.7.7.9`).
* Caveat for OSGi consumers: in an OSGi `Bundle-Version` the fourth part is the qualifier and is compared as a string,
  so `4.7.7.10` sorts before `4.7.7.9` there.
* *Current version: `4.7.7.1`.* It is set in two places that must be raised together:
  `projectVersion` in `dependencies.gradle` (the jar, OSGi `Bundle-Version` and published version derive from it)
  and `CommandLine.VERSION` in `src/main/java/picocli/CommandLine.java` (checked by `CommandLineTest.testVersion`).
* Release procedure: raise both to the version to release, then push the tag `v<version>`, for example `v4.7.7.1`.
  The release workflow only starts for four-part tags and fails if the tag and `CommandLine.VERSION` differ.
  The next cliwerk revision is `4.7.7.2`; after an upstream release 4.7.8 is merged (if upstream ever publishes it),
  the next version is `4.7.8.1`.

=== Legacy releases 4.7.8 to 4.9.4

Before this decision, cliwerk published its own releases under upstream-looking version numbers:
`io.github.wstein:picocli` 4.7.8, 4.7.9, 4.8.0 and 4.9.0 to 4.9.4 in the GitHub Pages Maven repository
(formerly also as tags `v4.7.8` ... `v4.9.4` and GitHub Releases titled "picocli 4.7.8" ... "picocli 4.9.4";
the owner has deleted those tags and GitHub Releases).
These were *cliwerk's own releases, not upstream picocli releases*; they are legacy lines of this fork.
Consequences:

* The legacy versions are numerically higher than `4.7.7.x`, so Maven and Gradle treat them as newer.
  Dynamic versions (`latest.release`, `+`, version ranges) and conflict resolution pick a legacy release over `4.7.7.x`.
  Consumers must pin the cliwerk version explicitly.
  Once the new coordinates `io.github.wstein:cliwerk` are in use (see <<Coordinates and distribution>>),
  the legacy versions stay under the old artifactId `io.github.wstein:picocli` and no longer compete with the new ones.
* The legacy artifacts are still in the GitHub Pages Maven repository (`maven/io/github/wstein/picocli/`).
  Open owner action, *not done*: decide whether they are removed there or kept as deprecated.
* Number overlap: if upstream publishes 4.7.8, 4.7.9, 4.8.0 or 4.9.0 to 4.9.4, that number is a real upstream release
  (`info.picocli:picocli`) and also a legacy cliwerk version (`io.github.wstein:picocli`).
  Since the legacy tags have been deleted, an upstream tag `v<x.y.z>` no longer collides with a tag in this repository.
  cliwerk's own versions always have four parts, so `4.7.8.1` cannot be confused with a legacy version,
  and the release workflow ignores three-part tags.

== Branch model

`develop`::
  The default and active branch. All cliwerk development is merged here, and releases are tagged from it.
`main`::
  Intended as a pure mirror of upstream picocli (decided 2026-10-24).
  It has been used for work proposed to upstream picocli (the fish completion of remkop/picocli#2463),
  which has been brought into `develop`. The owner plans to reset `main` to upstream;
  after that, `develop` is the only line carrying fork changes.

== Upstream syncs

Decided 2026-10-24: upstream is synced *release by release*.

* When upstream picocli publishes a release, its tag is merged into `develop` with a merge commit,
  through a draft pull request in which the conflicts are resolved and the base version
  (the first three parts, see <<Versioning>>) is raised to that release.
* The legacy tags `v4.7.8` to `v4.9.4` have been deleted (see <<Legacy releases 4.7.8 to 4.9.4>>),
  so fetching an upstream tag with the same name no longer collides with a cliwerk tag.
  Upstream tags are three-part and do not trigger the cliwerk release workflow.
* Target: an API compatibility check as part of the build verification (implemented opt-in and report-only, see Status below):
** Reference: the last merged upstream release, currently `info.picocli:picocli:4.7.7` from Maven Central,
   pinned explicitly (for example as `upstreamBaseVersion` in `dependencies.gradle`)
   rather than derived from the project's own group, artifactId or version.
** Tool: japicmp (Gradle plugin `me.champeau.gradle.japicmp`), comparing package `picocli`,
   failing on removed or binary-incompatibly changed public API and allowing additions
   (see <<Compatibility with upstream picocli>>).
** The bnd `baseline` setup inherited from upstream in `build.gradle` is not such a check:
   it compares against the highest `info.picocli:picocli` version below the version being built (not a pinned upstream release),
   bnd's semantic-versioning rules are expected to flag additions too unless the exported package version gets a minor increase,
   and it is not known to run in CI.
* Status: the check exists as the opt-in Gradle task `apiCompat` (`./gradlew apiCompat -PapiCompat`, `gradle/api-compat.gradle`)
  and the workflow `api-compat.yml`; it is report-only (`apiCompatBlocking = false`) and not part of `check`.
  Result against upstream 4.7.7: *0 binary-incompatible* changes and *6 source-incompatible findings that are excepted*:
  the annotation elements `helpSection()` of `@Option`, `@Parameters`, `@ArgGroup` and `@Command` and
  `helpSections()` and `showHelpSectionsNotice()` of `@Command` are new, but all have a default value,
  so they are source- and binary-compatible for users of the annotation (japicmp reports `METHOD_ABSTRACT_ADDED_TO_CLASS`
  because it cannot see the default). The exceptions are listed one by one, with justification, in
  `gradle/api-compat-exceptions.txt` (kind `annotation-element`, no wildcards) and are shown separately as "excepted" in the report;
  a new annotation element without default value would stay a finding.
* Upstream changes are brought into cliwerk manually by the maintainer.
  The weekly `upstream-sync-probe` workflow trial-merges the upstream default branch into `develop`
  to detect merge conflicts early; it never commits or pushes anything.

== Naming and identity rules

* The project name is *cliwerk* (lowercase in repository, artifact and file names).
* Do not use the name "picocli" for cliwerk releases, release titles, announcements or distributions.
  "picocli" refers to the upstream project only.
* Do not use the picocli logo for cliwerk.
* Keep upstream copyright and attribution notices intact (see `NOTICE`).
* The Java package `picocli` keeps the upstream name by decision (see <<Compatibility with upstream picocli>>).
* Transition: the module names (`picocli-spec`, `picocli-spec-tool`, ...),
  the published Maven coordinates (`io.github.wstein:picocli`, ...) and the GitHub Pages URLs
  referenced in the documentation (`wstein.github.io/picocli`) still carry the upstream name.
  The new coordinates are decided (see <<Coordinates and distribution>>), but not yet implemented.

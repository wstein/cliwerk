= cliwerk and upstream picocli
:toc: preamble

cliwerk is an independent, long-lived fork of https://github.com/remkop/picocli[picocli] by Remko Popma,
maintained by https://github.com/wstein[wstein] at https://github.com/wstein/cliwerk.
This page describes how the fork relates to upstream, how its branches are used, and the rules for its name.

== Relationship to upstream

* cliwerk started as a fork of picocli and keeps picocli's code, history and license
  (Apache License 2.0, see `LICENSE` and `NOTICE`).
* cliwerk is *not affiliated with or endorsed by the picocli project*.
  Problems found in cliwerk should not be reported to the picocli project unless they are
  reproducible with an upstream picocli release.
* The library API is still picocli's: the Java package is `picocli` and the upstream user manual at
  https://picocli.info applies to everything cliwerk has not changed.
  cliwerk is meant as a drop-in replacement for upstream picocli, see <<Compatibility with upstream picocli>>.
* cliwerk adds features on top of picocli (fish shell completion, `picocli-spec`, `picocli-spec-tool`,
  on-demand help sections; see the `README.md` and `CHANGELOG.md`).
  Some of them are proposed upstream as well (fish completion: https://github.com/remkop/picocli/pull/2463[remkop/picocli#2463]);
  whether upstream accepts them does not affect their availability in cliwerk.

== Compatibility with upstream picocli

cliwerk is a *drop-in replacement* for upstream picocli (decided 2026-10-24, see <<Decision log>>):

* The Java package stays `picocli`, and all public API names (classes, annotations, methods, attributes)
  stay as they are in upstream picocli. Only the Maven coordinates differ from upstream.
* Rule: the public API of `picocli.*` stays *additive*. cliwerk may add public types and members,
  but does not remove or incompatibly change public API that upstream picocli provides.
  Removing or changing public API needs a deliberate exception, recorded in the <<Decision log>>
  with the affected API and the reason.
* Consequence: cliwerk and upstream picocli (`info.picocli:picocli`) cannot be on the same classpath.
  Both contain the same fully qualified class names (`picocli.CommandLine`, ...), so whichever jar comes first wins.
  Because the Maven coordinates differ, Maven and Gradle do not see this as a version conflict and will not resolve it for you.
  If a dependency brings in upstream picocli transitively, exclude it or substitute cliwerk for it.
  Since the API is additive, code compiled against upstream picocli keeps working with cliwerk.
+
Maven, on each dependency that brings in upstream picocli:
+
[source,xml]
----
<dependency>
  <groupId>com.example</groupId>
  <artifactId>some-library</artifactId>
  <version>1.0</version>
  <exclusions>
    <exclusion>
      <groupId>info.picocli</groupId>
      <artifactId>picocli</artifactId>
    </exclusion>
  </exclusions>
</dependency>
----
+
Gradle, for all configurations, either exclude upstream picocli:
+
[source,groovy]
----
configurations.all {
    exclude group: 'info.picocli', module: 'picocli'
}
----
+
or substitute cliwerk for it (`using` needs Gradle 6.6 or later;
use the current coordinates until the new ones of <<Coordinates and distribution>> are implemented):
+
[source,groovy]
----
configurations.all {
    resolutionStrategy.dependencySubstitution {
        substitute module('info.picocli:picocli') using module('io.github.wstein:picocli:<version>')
    }
}
----
* Renaming the Java package (for example to `cliwerk`) remains possible later, but is deliberately deferred:
  it would touch almost every source file and make every upstream merge conflict broadly.

== Branch model

`develop`::
  The default and active branch. All cliwerk development is merged here, and releases are tagged from it.
`main`::
  An upstream-near staging branch. It has been used for work proposed to upstream picocli
  (the fish completion of remkop/picocli#2463), which is being brought into `develop`.
  Planned: `main` may be reset to the upstream commit; after that, `develop` is the only line carrying fork changes.

== Upstream syncs

Upstream changes are currently brought into cliwerk manually by the maintainer.
There is no automated upstream sync on `develop` yet.

== Naming and identity rules

* The project name is *cliwerk* (lowercase in repository, artifact and file names).
* Do not use the name "picocli" for cliwerk releases, release titles, announcements or distributions.
  "picocli" refers to the upstream project only.
* Do not use the picocli logo for cliwerk.
* Keep upstream copyright and attribution notices intact (see `NOTICE`).
* The Java package `picocli` keeps the upstream name by decision (see <<Compatibility with upstream picocli>>).
* Transition: the module names (`picocli-spec`, `picocli-spec-tool`, ...),
  the published Maven coordinates (`io.github.wstein:picocli`, ...) and the GitHub Pages URLs
  referenced in the documentation (`wstein.github.io/picocli`) still carry the upstream name.
  Changing them is a separate migration that has not been scheduled yet.
